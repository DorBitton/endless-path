# Firewalls, Netfilter, and NAT

## 🧠 The Core Concept

Linux firewalls do not inspect packets in user-space. The packet processing happens entirely inside the kernel via **Netfilter**. Tools like `iptables` and `nftables` are just user-space frontends that configure Netfilter.

### 1. The 5 Netfilter Kernel Hooks
Every packet traversing a Linux machine hits Netfilter hooks in a strict sequence:

1. **Prerouting:** Evaluated as soon as a packet arrives at the network card, before the kernel consults the routing table.
2. **Input:** Packets addressed to a local socket/process on this machine.
3. **Forward:** Packets addressed to another IP or interface (e.g. routed between subnets or sent to containers on a bridge).
4. **Output:** Packets generated by a local process on this machine.
5. **Postrouting:** Evaluated right before a packet leaves the physical wire or interface.

### 2. iptables vs. nftables
* **iptables (Legacy):** Rigid built-in tables (`filter`, `nat`, `mangle`) and fixed chains. IPv4, IPv6, ARP, and bridge traffic required separate binaries (`iptables`, `ip6tables`, `arptables`, `ebtables`). Rules are evaluated sequentially in the kernel.
* **nftables (Modern):** Completely modular. No default tables or chains exist until created. Combines IPv4 and IPv6 under one family (`inet`). Executes rules using an in-kernel bytecode virtual machine, offering higher performance and atomic ruleset updates.

## 🔄 NAT (Network Address Translation)

NAT rewrites packet headers in flight so private IP addresses (like container networks or home LANs) can communicate with public networks.

### The Office Mailroom Mental Model
* A container has an internal desk number (private IP `172.17.0.2`).
* External internet routers drop private IPs because they cannot route replies back to an internal desk.
* The Linux kernel acts as the mailroom clerk: it erases the desk number, writes the building's public street address (host IP) on the envelope, and tracks the connection in a table (conntrack).

### The Two Flavors of NAT
1. **SNAT / MASQUERADE (Source NAT - Outbound):**
   * **Where:** Evaluated at the **Postrouting** hook.
   * **What it does:** Rewrites the *sender's* source IP from the container IP (`172.17.0.2`) to the host public IP.
   * **Use case:** Container fetching packages from GitHub or making API calls to the internet.
   * *Masquerade* is a dynamic form of SNAT that automatically uses whatever IP is currently assigned to the outbound interface.

2. **DNAT (Destination NAT - Inbound / Port Forwarding):**
   * **Where:** Evaluated at the **Prerouting** hook.
   * **What it does:** Rewrites the *destination* IP and port from the host (`host-ip:8080`) to the private container (`172.17.0.2:80`).
   * **Use case:** `docker run -p 8080:80`.
   * **Why Prerouting?** The kernel must know the *real* destination IP before consulting the routing table, otherwise it would mistakenly treat the packet as local host traffic.

## ☸️ Containers & Kubernetes (The SRE Reality)

### 1. Docker and Bridge Networking
* Containers connect to a virtual bridge interface (`docker0`).
* To route packets between `docker0` and the host physical interface (`eth0`), Linux kernel forwarding must be active:
  ```bash
  sysctl net.ipv4.ip_forward
  # Must equal 1, or routed container packets get dropped immediately
  ```

### 2. The Docker Host Firewall Bypass Gotcha
* Docker writes raw Netfilter rules directly to implement port forwarding.
* If you set up a basic host firewall (like UFW or simple input rules) to block port 8080, Docker's DNAT rules in Prerouting often run first and forward the traffic straight into the container bridge.
* **Result:** External traffic reaches your container even though your host firewall appears to block the port.

### 3. The Dual-Backend Trap (`iptables-legacy` vs `iptables-nft`)
* Modern Linux distros provide `iptables-nft`, a translation layer letting legacy `iptables` commands write into `nftables`.
* If legacy container tooling writes to `iptables-legacy` while system services configure `nftables`, both rule engines run at the same time in the kernel.
* Packets can be silently dropped by one engine even if explicitly accepted by the other.

### 4. Kubernetes `kube-proxy` Evolution
In Kubernetes, `kube-proxy` routes Service virtual IPs (ClusterIP) to target Pod IPs:
* **iptables mode:** Generates random-probability chains for load balancing. For 5,000 services, this creates tens of thousands of rules with linear lookup time, causing latency and high CPU during updates.
* **IPVS mode:** Uses Linux IPVS kernel hash tables ($O(1)$ lookups) for large clusters.
* **nftables mode:** Native `nftables` backend introduced to resolve legacy iptables locking and scaling issues.
* **eBPF (Cilium, Calico eBPF):** Modern clusters often replace `kube-proxy` entirely by running eBPF programs attached to network sockets and interfaces, bypassing Netfilter completely.

## 💻 Essential Administrative & Triage Commands

```bash
# 1. View active nftables ruleset in full
sudo nft list ruleset

# 2. Stream live firewall events and monitor rule updates
sudo nft monitor

# 3. Reload ruleset from file atomically
sudo nft -f /etc/nftables.conf

# 4. Enable nftables service on system boot
sudo systemctl enable --now nftables

# 5. Verify IP forwarding is enabled for container routing
sysctl net.ipv4.ip_forward

# 6. Check which backend iptables points to on the host
update-alternatives --display iptables
```

## ⚡ Active Recall Flashcards

Why must Destination NAT (DNAT) for container port forwarding occur at the Prerouting hook instead of Input?::The destination IP must be rewritten to the container private IP before the kernel makes its routing decision, otherwise the packet is treated as local host traffic

What happens to outbound container traffic if net.ipv4.ip_forward is set to 0?::The Linux kernel refuses to route packets between the container bridge and physical network interfaces, dropping outbound traffic

Why does a container need Source NAT (SNAT or Masquerade) to access the public internet?::Containers have private RFC 1918 IPs that internet routers discard; the host must swap the container IP with its own routable IP

Why can Docker containers remain publicly accessible even when an administrator adds host firewall rules to block the port?::Docker writes DNAT rules directly into Netfilter, which redirect traffic at the Prerouting stage before standard host Input filter chains are evaluated

Why did large Kubernetes clusters migrate away from iptables-based kube-proxy?::iptables evaluates rules sequentially, causing high CPU usage, latency, and rule update lock contention at thousands of Services
